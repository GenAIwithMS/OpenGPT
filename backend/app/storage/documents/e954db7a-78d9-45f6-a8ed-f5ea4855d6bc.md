# Doctor Agent

WhatsApp assistant for a paediatric clinic. Parents book, move and cancel
appointments over WhatsApp; emergencies and "let me talk to the doctor" requests
are escalated to the doctor's own WhatsApp, and the doctor answers through the
same bridge. Built with FastAPI, SQLAlchemy, an OpenAI-compatible LLM
(OpenRouter by default) and the [OpenWA](https://github.com/open-wa/wa-automate-nodejs)
gateway.

## How a message flows

```
WhatsApp ──► OpenWA gateway ──► POST /webhook/openwa
                                      │
                    is the sender the configured doctor number?
                     │ yes                               │ no
                     ▼                                   ▼
             DoctorMessageRouter                   MessageRouter (patient)
             • case commands / chat mode           • lifecycle sweep
             • reply classification (LLM)          • active case? forward to doctor
             • tool assistant (lookups)            • emergency keywords? open case
                                                   • otherwise LLM agent + booking tools
```

* `app/main.py` – webhook, signature check, admin endpoints.
* `app/router.py` – patient side. Reads history, opens cases, calls the LLM agent.
* `app/doctor_router.py` – doctor side. Explicit case routing, chat mode, tool assistant.
* `app/agent/` – prompts, tool schemas, tool implementations (`tools.py` for
  patients, `doctor_tools.py` for the doctor), intent keywords.
* `app/rag/` – knowledge-base loader and BM25 retriever behind
  `search_doctor_info`.
* `app/services/` – appointments, emergency cases, handoffs, notifications,
  Google Sheets sync.
* `app/integrations/` – WhatsApp (OpenWA), Google Calendar, Google Sheets, each
  with a stub used by the tests.
* `app/repositories/` – all database access.
* `app/workers/` – background worker (reminders, expiry sweep).

## Setup

Requires Python 3.13+.

```bash
python -m venv .venv && source .venv/bin/activate
pip install .
cp .env.example .env          # fill in the values below
uvicorn app.main:app --reload # API on :8000
python -m app.workers         # background worker (every 5 min)
```

Tables and any missing columns are created automatically at startup for the
local sqlite database. For Postgres run `alembic upgrade head` once.
`docker-compose.yml` starts Postgres, the API and the worker together.

### Required settings (`.env`)

| Key | Meaning |
|---|---|
| `API_KEY` | LLM API key (OpenRouter). `LLM_BASE_URL`, `LLM_MODEL` optional. |
| `DATABASE_URL` | `sqlite:///./doctor_agent.db` or a Postgres URL. |
| `WHATSAPP_PROVIDER` | `openwa` in production, `stub` for local runs and tests. |
| `OPENWA_BASE_URL`, `OPENWA_API_KEY`, `OPENWA_SESSION_ID`, `OPENWA_WEBHOOK_SECRET` | Gateway connection. The webhook signature is verified when the secret is set. |
| `DOCTOR_WHATSAPP_NUMBER` | The **only** number treated as the doctor. Any format (`+923…`, `923…`, `03…`). |
| `DOCTOR_NAME`, `CLINIC_MAPS_LINK`, `CLINIC_LOCATION`, `CLINIC_PHONE` | Injected into the patient prompt and escalation messages. |
| `APPOINTMENT_START_HOUR`, `APPOINTMENT_END_HOUR`, `MAX_DAILY_APPOINTMENTS` | Clinic hours (default 4 pm to 8 pm) and tokens per day (default 40). No fixed slot times. |
| `LLM_TEMPERATURE`, `LLM_MODEL_CLASSIFIER` | Sampling temperature for every LLM call (default 0). Optional cheaper model for the doctor-reply classifier; defaults to `LLM_MODEL`. |
| `HANDOFF_TTL_MINUTES` | How long a doctor takeover stays active without an explicit `resolve`. |
| `EMERGENCY_REMINDER_MINUTES`, `EMERGENCY_PENDING_TTL_HOURS` | Reminder to the doctor, then auto-close of an unanswered case. |
| `TALK_REQUEST_TTL_HOURS` | Unanswered talk-to-doctor messages are closed silently after this (default 48). |
| `EMERGENCY_EXPIRY_GRACE_MINUTES`, `EMERGENCY_REOPEN_WINDOW_MINUTES` | Auto-close waits at least this long after the reminder; a plain doctor reply within this window of an auto-close reopens the case. Both default to 30. |
| `CALENDAR_PROVIDER`, `CALENDAR_ID`, `CALENDAR_CREDENTIALS` | Optional Google Calendar mirror. See `setup_calendar.py`. |
| `SHEETS_PROVIDER`, `SHEETS_SPREADSHEET_ID`, `SHEETS_WORKSHEET`, `SHEETS_HISTORY_DAYS` | Optional Google Sheets mirror of the appointment book (`google`, `stub` or `off`). Same credentials file as the calendar. |
| `KNOWLEDGE_BASE_DIR`, `RAG_TOP_K` | Folder of `.md`/`.txt` files about the doctor and clinic (default `doctor_info`), and how many chunks a lookup returns. |
| `ADMIN_API_KEY` | Protects the `/admin/*` endpoints (`X-API-Key` header). |

Configure OpenWA to POST message events to `https://<host>/webhook/openwa` and
enable LID-to-phone resolution so senders arrive with a real phone number.
Unresolved `@lid` senders are never treated as the doctor.

## Patient side

The LLM agent follows `app/agent/prompts.py`. Key rules:

* **Tokens, not times.** There are no fixed appointment times. Each day the
  clinic issues sequential tokens (up to `MAX_DAILY_APPOINTMENTS`) and patients
  are seen in token order between `APPOINTMENT_START_HOUR` and
  `APPOINTMENT_END_HOUR`. A booking is a token for a date; the parent is told to
  come between 4 PM and 8 PM with the token number. A cancelled token number is
  never reissued on that day. Today stays bookable until the clinic closes.
* Always resolve dates with `get_current_datetime` and check `check_availability`
  before booking. Replies to parents are in Urdu script; tool arguments (names,
  reasons) are always English / Latin letters, and child names are matched
  ignoring case, spacing and script so `اسلم` does not duplicate `Aslam`.
* **One token per number.** A parent holds at most one live appointment.
  Booking again for the same day updates the existing token. Booking another
  day moves it and cancels the old token, but only with `confirm=true`, which
  the model may pass only after the parent explicitly agreed; the tool refuses
  otherwise. A question or doubt about an existing token is never a change
  request.
* Emergencies: keyword detection in code (`app/agent/intent.py`, English and
  Roman Urdu) opens a case before the LLM runs; the LLM can also call
  `report_emergency` with a short summary of the chat for the doctor.
* Talk to the doctor: the assistant never offers to contact the doctor. Only
  when the parent explicitly asks, and once the reason is clear (otherwise it
  asks politely first), it calls `request_human_handoff` with the reason and a
  2-3 sentence summary. The tool refuses reasons with no topic ("wants to talk
  to the doctor"). This is a **message, not a case**: the doctor gets who is
  asking, why, and the summary (never the raw transcript); the parent is not
  put on hold, the assistant keeps booking and answering and only defers on
  that topic (extra details for the doctor go through `notify_doctor`). The
  doctor's first reply is delivered and closes the message. No reminders; an
  unanswered message is closed silently after `TALK_REQUEST_TTL_HOURS`. A real
  emergency arriving while a message is pending closes it and opens a case.
* While a case is open, every patient message (text, or a note for media) is
  forwarded to the doctor with the patient's name and number, and the assistant
  stays out of the conversation.

Patient tools: `identify_patient`, `book_appointment`, `reschedule_appointment`,
`cancel_appointment`, `check_availability`, `get_appointment_status`,
`get_my_info`, `get_current_datetime`, `search_doctor_info`, `report_emergency`,
`notify_doctor`, `request_human_handoff`.

### Questions about the doctor and clinic

Facts about the doctor and clinic live in `doctor_info/` as plain markdown
(`doctor_information.md` today: qualifications, experience, awards, clinic
address, services, vaccines, conditions treated, when to consult, clinic
timings and the token system, and payment: nothing is collected online, the
fee is paid at the clinic after the consultation). The
`search_doctor_info` tool splits those files into heading-scoped chunks and
ranks them with BM25 (pure Python, no embedding API), with a synonym table so
Hinglish phrasings such as "doctor ki degree", "teekay", or "clinic ka pata"
find the English text. The prompt tells the model to call it first for any such
question, answer only from the results, and say when nothing was found.

To add knowledge, drop another `.md` or `.txt` file into the folder or edit the
existing one; the index rebuilds on the next question, no restart needed. Keep
facts under clear headings, one topic per section, because each section is
retrieved as a unit.

## Doctor side

Every case has a number (from 1001). The doctor gets one WhatsApp notification
per case and answers from their own phone.

| Doctor sends | Effect |
|---|---|
| `1001: <text>` | Reply to case 1001. While pending the text is classified (confirm, instruct, not an emergency); in chat mode it is relayed word for word. Medicine names and doses are always relayed verbatim. For a talk-to-doctor message the reply is delivered and the message closes. |
| `chat 1001` | Take over the case. Every plain message after this goes straight to that patient. |
| `resolve [1001]` | Close the case; the assistant resumes for that patient. |
| `cases` | List active cases; the chat target is marked. |
| `ask <question>` | Ask the tool assistant even while in chat mode. |
| `help` | Show this list. |

Plain messages with no command: relayed to the chat patient if chat mode is on,
interpreted for the single pending case if there is exactly one, otherwise
handled by the tool assistant. A reply the classifier cannot use also falls
through to the tool assistant. A leading `/` is optional.

The doctor's identity is checked in code only (`app/doctor_auth.py`); the tool
assistant is told the sender is already verified and never asks for credentials.
It answers the doctor only in Urdu script, whatever language the doctor writes
in; case alerts, reminders and command feedback stay English. Reworded relays to
parents are produced in Urdu; verbatim relays keep the doctor's exact words.
It receives the doctor's recent conversation as history, and every case alert,
reminder and auto-close notice sent to the doctor is stored in that conversation,
so "tell him payment is after treatment" is understood in context.

Late replies: `1001: <text>` or `chat 1001` on a closed case reopens it and
applies the reply. When no case is active and one was auto-closed within
`EMERGENCY_REOPEN_WINDOW_MINUTES`, a plain reply the classifier can act on
reopens that case; anything else goes to the tool assistant.

Doctor tools (used by the tool assistant): `patient_lookup` (phone in any
format, ID or child name), `check_schedule` (tokens issued and remaining on a
date), `view_appointments` (booked tokens for a date, default today), and
`appointment_history` (past appointments over a date range with per-day
attended / cancelled / no-show counts, e.g. "how many did we see yesterday").

### Case lifecycle

```
EMERGENCY_PENDING ──doctor confirms / chat──► HUMAN_HANDOFF ──resolve──► RESOLVED
       │  reminder after EMERGENCY_REMINDER_MINUTES                          │
       └─ no reply for EMERGENCY_PENDING_TTL_HOURS ─────────────────────► EXPIRED
       ▲   (never sooner than EMERGENCY_EXPIRY_GRACE_MINUTES after the reminder;   │
       │    patient told to call the clinic)                                      │
       └──────────── doctor replies to the closed case (reopened) ────────────────┘
```

The sweep that sends reminders and expires cases and handoffs runs on every
webhook and in the worker, so nothing stays stuck if the worker is down.

## Google Sheets mirror

Every appointment change (new token, update, move, cancel) rebuilds a worksheet
in a Google Sheet so the doctor can browse the appointment book outside
WhatsApp. The database stays the source of truth: each sync clears the
worksheet and writes all appointments from the last `SHEETS_HISTORY_DAYS` days
onward in one request, sorted by date and token, with cancelled rows kept and
marked. The sync runs in a background thread and never delays a reply; the
worker repeats it every cycle as a safety net.

Columns: Token, Date, Time (the clinic window, e.g. `4:00 PM - 8:00 PM`),
Child, Age, Guardian, Phone, Reason, Status, Booked At, Last Updated,
Appointment ID.

Setup, once:

```bash
python setup_calendar.py --client-id ... --client-secret ... --create-sheet
```

This re-runs the Google consent with the Calendar and Sheets scopes, creates the
spreadsheet in your Drive, and prints the `SHEETS_*` lines for `.env`. To use an
existing spreadsheet instead, set `SHEETS_PROVIDER=google` and
`SHEETS_SPREADSHEET_ID` to the id from its URL; the worksheet is created if
missing. When configured, the doctor assistant knows the sheet link, so
"send me the appointments sheet" returns it.

## Admin endpoints

All need `X-API-Key` when `ADMIN_API_KEY` is set.

* `GET /health`
* `GET /admin/availability?date_str=YYYY-MM-DD` – tokens issued / remaining.
* `POST /admin/expire-handoffs`
* `POST /admin/sweep` – reminders, case expiry, handoff expiry.
* `POST /admin/sheets-sync` – rebuild the Google Sheet from the database.

## Tests and evaluation

```bash
python -m pytest tests/test_flows.py -q   # flows and guardrails, no network
python tests/smoke.py                     # imports + 3-level implementation eval
python -m model_evaluation.evals.component --mode direct   # tool components offline
```

Both test entry points use a throwaway sqlite file and the stub WhatsApp
service, so they never touch the real database or message the doctor.
`model_evaluation/` holds the LLM evaluation harness (agent mode calls the
real model); `eval-docs/` describes the metrics.
